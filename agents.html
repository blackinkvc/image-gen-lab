Agent 不是新模型，是把模型放进循环：调工具、读结果、改计划、再调工具。 决定它能不能干活的，往往不是模型分数，而是权限、沙箱、失败恢复和成本上限。

结论先行 / VERDICT

  1. 编码 Agent 是第一个跑通的场景。代码有编译器、测试和版本控制，反馈可验证，所以 Agent 能自我纠错；通用办公场景缺少这套「判卷人」。
  2. 协议比模型更影响生态。MCP 统一了「模型怎么接工具」，A2A 试图统一「Agent 怎么互相调用」。协议稳定后，工具方才有动力接入。
  3. 长程可靠性仍是短板。任务超过十几步后，错误会累积；当前工程解法是拆任务、加检查点、限制单步权限，而不是换更大的模型。
01

能力栈

一个能用的 Agent 至少由五层组成，缺一层就会在真实任务里暴露：

AGENT STACK自上而下
编排层    plan → act → observe → replan   任务拆解、循环控制、停止条件
工具层    MCP / function calling       文件、终端、浏览器、API
记忆层    context + 外部存储          上下文压缩、检索、检查点
执行层    sandbox / VM / 容器          权限、网络、文件系统隔离
模型层    reasoning model               规划质量与工具调用稳定性

常见误解是把 Agent 当成「更聪明的模型」。实际上同一模型换一套工具与沙箱， 任务成功率会差出数倍——工程层的权重不低于模型层。

权限是最容易被忽略的一层。给 Agent 一个能写文件、能发网络请求的终端，等于把整台机器交给它；生产环境必须按最小权限切分，并给每一步留可回滚的检查点。

02

协议与接口

2024 到 2025 年，Agent 生态最大的变化不是模型，而是接口开始标准化。

协议提出方时间解决什么状态
MCPAnthropic2024-11模型 / 客户端如何统一接入外部工具与数据源事实标准
A2AGoogle2025-04不同厂商的 Agent 之间如何发现与协作推进中
AGENTS.md社区 / 多家2025把仓库里的操作约定写给编码 Agent 看约定俗成

MCP 是「纵向」接口：Agent 往下接工具。A2A 是「横向」接口：Agent 之间互相调用。两者不冲突，但成熟度差一截。

04

评测：看什么，不看什么

本页不收录具体分数，因为同一模型在不同脚手架、不同工具集下的成绩差异很大。 更有参考价值的是「这个基准考的是什么」。

SWE-bench Verified 编码

给真实仓库的 issue，看能否改到测试通过。考的是定位、修改与验证的完整闭环。

Terminal-Bench 终端

在命令行里完成多步系统任务，考工具使用与环境理解。

τ-bench 对话 + 工具

模拟客服等业务对话，同时调用后端工具，考规则遵循与状态一致性。

OSWorld / WebArena 操作

在真实桌面或网页环境里完成任务，考视觉定位与长程操作。

共同问题：基准会泄漏进训练集；脚手架不同导致不可比；单次成功率不反映成本。看结论时要问「跑了几次、什么工具、花了多少 token」。

05

工程约束与风险

提示注入网页与文件里的指令会被当成任务执行，必须做来源隔离。
权限过大默认可写可联网，等于把生产环境交出去。
错误累积步数越多，单步小错越容易滚成整体失败。
成本失控循环没有硬上限时，token 消耗会指数级上涨。
可观测性必须记录每一步的输入、工具调用与结果，否则无法复盘。
人机边界高风险动作（付款、删除、发布）应强制人工确认。
