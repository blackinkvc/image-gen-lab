01

它是什么

Z-Image Base 与 Turbo 共用同一套架构：16 通道潜空间、Qwen3-4B 文本编码器、同一个 ae.safetensors VAE。区别在训练目标——Turbo 是 8 步蒸馏， Base 是完整的多步模型。同架构意味着两者的潜变量可以直接对接，这也是当初尝试双采的前提。

分工上，Base 负责「把结构画对」，Turbo 负责「快速重采样细节」。双采实验就是想把这个分工串起来： Base 30 步定型，Turbo 8 步低 denoise 精修。结论是这条链在本机装不下，详见 方案 04。

02

怎么跑

节点链与 Turbo 完全一致，只改步数、cfg 与 denoise。下面是双采实验里用的第一段配置。

NODE GRAPHBase 第一段 / 双采实验配置
UNETLoader        z_image_bf16.safetensors  weight_dtype=default
CLIPLoader        qwen_3_4b.safetensors        type=lumina2
VAELoader         ae.safetensors
ModelSamplingAuraFlow  shift=3.0
CLIPTextEncode    positive / negative
EmptyLatentImage  832 × 1216  batch=1
KSampler          steps=30 cfg=4.0 sampler=res_multistep
                  scheduler=simple denoise=1.00
VAEDecode         # 双采时此处不落盘，直接接 Turbo 续采

未定型：30 步 / cfg 4.0 来自双采实验的既定配置，没有做过 Base 单独的步数与 cfg 扫描。采样器与调度器沿用 Turbo 的一套，未单独验证是否最优。

06

优缺点

预期优势 / 未验证

  • 非蒸馏 + 30 步，理论上低频（构图、体块、姿态）更稳。（推断）
  • cfg 4.0 比 Turbo 的 1.0 有更强的提示词约束力。（推断）
  • 与 Turbo 同架构、同 VAE，潜空间可直接对接。（结构事实）

代价 / 已验证

  • 30 步，单张成本至少是 8 步的数倍。（机制推断，未计时）
  • 与 Turbo 同时常驻会 OOM，本机装不下两套 UNET。（实测）
  • 没有 IPAdapter / ControlNet，控制力仍不如 SDXL。（结构事实）
  • 当前没有任何可用产出，无法进入交付链。（事实）
07

没验证的 / 数据限制

  • 独立跑单张：从未执行，耗时与显存全部为 null。
  • 步数 / cfg 扫描：30 / 4.0 是既定值，没有 20 步、40 步、cfg 3.0 的对照。
  • 画质对照：Base 与 Turbo 在同一 prompt 下的差异没有图，只有机制描述。
  • 串行装载：先卸 TE 再换 UNET 的降内存方案未做端到端测试，已随双采一起放弃。
  • 权重体积：11–12 GiB 是按同架构估算，未精确读取文件。
